# 07 — Lessons Learned (this session)

An honest accounting of what went wrong in this session, why, and what should change.
Written because asked for directly — not softened.

## Mistakes, false alarms, and wasted steps

| # | What happened | Cause | Lesson |
|---|---|---|---|
| 1 | CRLF line endings got written into `install-nms.sh` (and other files) by my own edits, breaking the first real install test (`set: pipefail: invalid option name`) | This Windows environment's edit tooling writes CRLF regardless of the file's actual line endings; I never byte-verified line endings after editing a script meant to run on Linux, and had no `.gitattributes` guard in place yet | Byte-verify line endings (`tr -d '\n' \| tr -cd '\r' \| wc -c`, not `od -c \| grep`) immediately after editing any script that will run on Linux, every time — don't wait until it breaks. Add `.gitattributes` *before* the first script edit, not after discovering the bug |
| 2 | Raised a false alarm that already-**pushed public commits** were CRLF-corrupted, when they never were | Diagnosed with an unreliable method (`od -c \| grep -o '\\r' \| wc -l`) that doesn't actually count real CR bytes reliably, and trusted the alarming result without cross-checking against a second method before reporting it as fact | Verify a measurement technique against a known-good and known-bad case before trusting it for a high-stakes diagnosis. The more alarming a finding, the more it deserves independent confirmation before being reported |
| 3 | Deliberately re-ran `install-nms.sh` a second time to exercise new code paths (`ISS-09`/`ISS-10`), which triggered `apt --reinstall` to revert already-applied branding patches (`ZBase.php`, `favicon.ico`) and then aborted at the known non-idempotent schema-import step — leaving the live site half-reverted and broken. I then reported the specific things I was testing (backup message, ERR trap) as confirmed working, without re-running the *full* verification checklist to check for side effects elsewhere | Treated the second run as an isolated unit test of the new code, and declared success based on the narrow thing being tested, not the system as a whole | After *any* write operation on a shared test VM — even a "deliberate test" expected to fail in a specific way — re-run the **full** verification checklist before declaring anything verified, not just the specific behavior under test. A partial failure can have side effects outside the failure path itself |
| 4 | The verification process itself (not just one lapse) only ever checked `curl -sI` status codes and a `grep -c zabbix` count on the anonymous login page. It missed a completely broken authenticated app — broken dashboard routing, the Zabbix "Warning" fallback title, and the stock Zabbix favicon — that the user saw in the browser within seconds | `HTTP 200` was treated as sufficient evidence of "working," and only the one page nobody needs to log in to see was ever checked. This was baked into how `md/05`'s checklist was originally written, not a one-off slip | `HTTP 200` proves a server responded, not that the content is correct. Verification has to simulate what a real user actually does — log in, navigate — not just probe surface signals on the one page that happens to need no authentication. Fixed in `md/05`'s authenticated-session-walk addition, but should have been there from the first draft |
| 5 | `apt-get autoremove --purge -y` removed `snmpd` and deleted `/etc/snmp/`, despite being told explicitly, one message earlier, "snmpd: leave it" | Ran a broad cleanup command with `-y` without previewing what it would actually remove, even with an explicit "leave this alone" instruction already on the table | Before running any broad/blanket command (`autoremove`, `purge`, `--reinstall`) when something specific was told to be protected, preview its effect on that specific thing first — never assume a generic cleanup command won't touch it |
| 6 | `md/06`'s offline-install-strategy numbers were guessed, not measured, and several were significantly wrong: source tarball guessed at "50–80MB compressed" (actual ~42MB); Zabbix `.deb`s guessed at "~105MB" by conflating total VM disk space freed with actual download size (actual ~19.8MB); the Ubuntu dependency closure guessed at "several hundred MB to ~1GB" (actual ~35.8MB); and I asserted vendor apt repos "typically only keep the current point release" without checking (every release since 7.4.0 was still live) | Wrote confident-sounding quantitative claims without doing the live lookups that were readily available the whole time (`curl -I`, apt `Packages` index queries) — the checks were easy and I didn't do them until explicitly told to in a later step | When a document makes a quantitative claim that can be verified with a quick live check, do the check instead of estimating — especially before presenting an estimate as researched fact. Mark genuinely unverifiable numbers `⚠️ needs confirmation` rather than guessing with false precision |
| 7 | The same scheduled-wakeup prompt kept re-firing as what looked like duplicate user turns, several times across the session, costing time to notice and dismiss each time — and I was never able to fully account for why, since `CronList`/`ScheduleWakeup(stop)` always came back clean when checked | Used `ScheduleWakeup` to self-pace waiting on a long-running background SSH/install command, when the background-task notification mechanism (which doesn't have a replay risk) was the correct tool for that situation | Don't reach for `ScheduleWakeup` just to wait on a backgrounded tool call — let the task-notification system do that. Reserve `ScheduleWakeup` for actually self-paced polling of external state the harness has no other way to observe |
| 8 | In reporting `ISS-26`/`ISS-27`, the favicon finding risked reading as "the Vizoure favicon branding is incomplete / missing," when it isn't — `branding/logos/favicon.ico` exists in the repo and `apply-branding.sh` already copies it to both required locations correctly on a normal run. The *only* real gap was that `ISS-26`'s reinstall-then-abort sequence reverted the UI-root copy and nothing re-verified it afterward — a verification gap, not a missing-asset or missing-logic gap | Logged the symptom (stock favicon visible in browser) as a branding-coverage issue without being explicit enough that the branding asset and the script logic for it are both already correct and complete | State plainly, every time, which layer a finding belongs to (asset missing vs. logic missing vs. verification missing vs. a one-off side effect of something else) — don't let a correctly-working piece of branding get misread as unfinished work just because a symptom of an unrelated bug happened to look like a branding gap |
| 9 | During the SSH-refused incident, asserted a specific root-cause theory (`apt upgrade` stuck on an interactive debconf prompt, same class as the earlier stuck-`unattended-upgrades` incident) as the likely explanation, in writing, before it was confirmed — and it was probably wrong. Once reconnected, there was no evidence of an actual interactive hang; it was just a slow `apt upgrade` plus a temporary `sshd` restart | Pattern-matched to a similar-looking prior incident under time pressure (the connection was down and I wanted to give a useful theory) without being able to verify it before the connection came back | Label a plausible-but-unconfirmed theory as exactly that when first raised, not as the likely explanation — especially when it can't be checked yet. It's fine to guess at a cause while blocked; it's not fine to let the guess read as settled |
| 10 | Spent real investigation time on the `ha_node` table's `status=3` row during the `ISS-26` root-cause hunt, without being able to confidently interpret what that status code means (uncertain recall of Zabbix's internal enum), before finding the actual, decisive evidence (the reverted `ZBase.php` patch) through a more direct check | Chased a database-level signal that looked suspicious before trying a more direct, simpler check (grep the actual file content for the expected patch) | When investigating a broken feature that a script is supposed to patch, check whether the patch is actually present *first* — it's more direct and more decisive than inferring backward from a status code whose exact meaning isn't confidently known |
| 11 | Backgrounded a long-running SSH install command with a manual shell `&` instead of the Bash tool's `run_in_background`, creating several minutes of confusion about whether the command was actually running or had died, before switching to the tool's proper mechanism | Reached for a shell-level shortcut instead of the harness-level one that's actually tracked and notifies on completion | Use the tool's own `run_in_background` for anything expected to run long, every time — a bare `&` inside a command string isn't tracked the same way and makes it harder to tell what state the command is actually in |
| 12 | Early in the session, reported "this checkout is not a git repository" based on checking only the parent folder (`D:\projects\vizoure-nms`) — a real `.git` existed one level down inside `Vizoure/` the whole time, with `origin` already configured and in sync. This went uncorrected for a significant part of the session until a later, unrelated check happened to reveal it | `git status` only searches upward from the current directory for a `.git` — it doesn't search downward into subdirectories — and I never explicitly checked the subdirectory itself | When checking whether something is a git repository (or any similarly structural fact), check the actual directory in question directly, not a parent, even if checking the parent seems like the obvious/natural starting point |

## Patterns across these, worth naming directly

- **Declaring success on partial evidence**, repeatedly (#3, #4, and the overall arc that led to this STOP instruction): testing the specific thing asked for and reporting "verified" without checking whether anything else broke, or whether the check itself was deep enough to catch a real failure.
- **Trusting a measurement or theory without cross-checking it**, especially under time or connectivity pressure (#2, #6, #9): writing down a number or an explanation that sounds right instead of confirming it when confirmation was actually available.
- **Not previewing before broad or destructive commands**, even with an explicit instruction already on the table to protect something specific (#5).
