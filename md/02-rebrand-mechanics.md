# 02 — Rebrand Mechanics

How "Zabbix" becomes "Vizoure" in a running install, in the order it actually happens.
Four layers, each independent of the others, each with its own trigger. Paths are
relative to the repo root unless stated otherwise.

---

## Layer 0 — Packages (not rebranded)

`scripts/install-nms.sh` step `[4/9]` installs the **official, unmodified** Zabbix apt
packages from `repo.zabbix.com` (`zabbix-server-mysql`, `zabbix-frontend-php`,
`zabbix-apache-conf`, `zabbix-sql-scripts`, `zabbix-agent`). Binary names, service unit
names (`zabbix-server`, `zabbix-agent`), and the on-disk path `/usr/share/zabbix/ui`
all stay as Zabbix named them. README's "Technical Notes" states this is deliberate,
for apt compatibility. Nothing in this repo changes it on Linux.

## Layer 1 — Database rows

Triggered from two places, with **different, drifted** SQL:

### `scripts/install-nms.sh`, step `[5/9]`
Runs, in order, against the freshly-imported schema:
1. `UPDATE hosts SET name = REPLACE(name,'Zabbix','Vizoure') WHERE name LIKE '%Zabbix%' AND status=3` — status 3 = template hosts only.
2. `UPDATE hosts SET vendor_name = 'Vizoure' WHERE vendor_name = 'Zabbix' AND status=3`
3. `UPDATE actions SET name = REPLACE(name,'Zabbix','Vizoure') WHERE name LIKE '%Zabbix%'`
4. `UPDATE triggers SET description = REPLACE(description,'Zabbix','Vizoure') WHERE description LIKE '%Zabbix%'`
5. `UPDATE items SET name = REPLACE(name,'Zabbix','Vizoure') WHERE name LIKE '%Zabbix%'`
6. `UPDATE usrgrp SET name = 'Vizoure Administrators' WHERE name = 'Zabbix administrators'`
7. `UPDATE users SET name='Vizoure', surname='Administrator' WHERE username='Admin'`
8. `UPDATE media_type SET smtp_email = 'noreply@vizoure.local' WHERE smtp_email = 'zabbix@example.com'`
9. `UPDATE images SET name = REPLACE(name,'Zabbix','Vizoure') WHERE name LIKE '%Zabbix%'`
10. `UPDATE hosts SET host = REPLACE(host,'Zabbix','Vizoure') WHERE host LIKE '%Zabbix%' AND status=3` — this is the one place the **technical** `host` identifier (not just the display `name`) gets rewritten, and it's scoped to template hosts (`status=3`) only, so live monitored hosts' technical identifiers are never touched.
11. A separate heredoc (`/tmp/vizoure_desc_fix.sql`) runs **11 chained `UPDATE hosts SET description = REPLACE(REPLACE(REPLACE(...` statements**, each nesting 4–7 `REPLACE()` calls (MySQL has no practical limit on nesting depth, but the script keeps each statement to ≤7 for readability/diffability), covering specific multi-word phrases found in template descriptions: "Zabbix Agent (zabbix-agent2)", "Zabbix Java Gateway", "Zabbix 7.4.", "the local Zabbix server", "by Zabbix via HTTP", etc. This is phrase-targeted, not a blanket find/replace, because template description text contains prose, not just product names.
12. Three `REGEXP_REPLACE` calls at the end of that heredoc **strip** (don't rename) lines referencing the Zabbix forum, `zabbix.com/documentation`, and "Generated by official Zabbix template tool" — these are removed outright since there's no Vizoure equivalent to redirect to.
13. `log_bin_trust_function_creators` is set to `1` before all this and back to `0` after — required because `REGEXP_REPLACE`/stored-function-like operations in MySQL need it when binary logging is on.

### `scripts/upgrade.sh`, step `[5/6]`
Re-runs only **7** of the above statements (name/vendor_name/host on hosts, triggers,
items, actions, images) — it does **not** re-run the `usrgrp`, `users`, `media_type`
renames, and it does **not** re-run the 11-statement description heredoc or the
`REGEXP_REPLACE` cleanups. Any template whose description text is newly introduced by
a Zabbix point-release upgrade will keep "Zabbix" wording until the next full install.
⚠️ needs confirmation whether this is intentional (those rows are assumed already
renamed from the original install and never reset) or a drift bug.

## Layer 2 — Installed UI files

`branding/apply-branding.sh` runs after Layer 0 and Layer 1, against the **live,
already-installed** tree at `/usr/share/zabbix/ui` (not against any source checkout —
see `01-repo-inventory.md` for the distinction from the unused `branding-patch.sh`).
11 (plus 2 extra, unnumbered) numbered steps:

| Step | Target | Action |
|---|---|---|
| `[1/11]` | `assets/img/logo.png`, `logo-compact.png`, `favicon.png`/`.ico` (both at `assets/img/` and UI root), touch icons (76/120/152/180/192px) | Downloads from `branding/logos/` on GitHub `main`, resizes with `convert` (ImageMagick) |
| `[2/11]` | `assets/styles/{blue-theme,dark-theme,hc-dark,hc-light}.css` | Appends a `.header-logo img, .sidebar-logo img { max-height: 40px !important; }` block; retries up to 30s waiting for the CSS files to exist (package-unpack timing) |
| `[3/11]` | `local/conf/brand.conf.php` (new file) | Defines `BRAND_LOGO`, `BRAND_LOGO_SIDEBAR`, `BRAND_LOGO_SIDEBAR_COMPACT`, `BRAND_FOOTER`, `BRAND_HELP_URL`. Zabbix's own `CBrandHelper` class reads this file — its presence is what makes Zabbix's stock frontend auto-suppress the Support/Integrations links (see Step 5 below); it's not a custom patch, it's Zabbix's built-in white-labeling hook |
| `[4/11]` | `app/partials/layout.htmlpage.footer.php` | `sed`: `Zabbix SIA` → `Vizoure` in the footer copyright comment |
| `[5/11]` | `include/views/general.login.php` | Python exact-block-match: removes the entire Help/Support `CDiv` block from the login page (only runs if the exact expected PHP block text matches — silently warns and skips otherwise) |
| `[6/11]` | `include/classes/helpers/CMenuHelper.php` | Python exact-block-match: removes the sidebar "Help" `CMenuItem` the same way |
| `[7/11]` | `include/defines.inc.php` | `sed`: `define('ZBX_TITLE', ...)` → `'Vizoure NMS'`. **Caveat:** no `ZBX_TITLE` define exists in the vendored `zabbix-master` (8.0.0rc2) reference tree — unverified against real 7.4.9 (see `01-repo-inventory.md`) |
| `[8/11]` | `app/partials/administration.system.info.php` | `sed` × 3: "Zabbix server is running" → "Vizoure NMS Server Status", "Zabbix server version" → "Vizoure NMS Version", "Zabbix frontend version" → "Vizoure Web Console Version" |
| `[9/11]` | `include/classes/html/CHostAvailability.php` | `sed`: the `ZBX` availability-icon label → `VIZ` |
| `[10/11]` | `app/views/administration.script.edit.php`, `app/controllers/CControllerActionLogList.php`, `CControllerProblemView.php`, `app/views/host.wizard.edit.php`, `app/views/administration.authentication.edit.php` | A grab-bag of single-string `sed`s: "Zabbix agent" labels, CSV export filenames (`zbx_actionlog_export.csv` → `vizoure_actionlog_export.csv`, same for problems export), host wizard text, login form string |
| `[11/11]` *(numbered 11 but not the last step — see below)* | Apache restart | `systemctl restart apache2` |

**Unnumbered steps after `[11/11]`** (the script's step counter is inconsistent — these
run after the "restart Apache" step is printed, meaning the Apache restart at `[11/11]`
is not actually last in execution order even though it's labeled last):
- More scattered single-string `sed`s: `administration.system.info.php` ("Global
  scripts on Zabbix server"), `discovery.inc.php` (`SVC_AGENT` label),
  `items.inc.php` (`ITEM_TYPE_ZABBIX`, `ITEM_TYPE_INTERNAL`, `ITEM_TYPE_TRAPPER`,
  `ITEM_TYPE_ZABBIX_ACTIVE` labels — 4 separate patches to the same file),
  `administration.timeouts.edit.php`, `CMediatypeHelper.php` (default SMTP email,
  redundant with the Layer-1 DB UPDATE on `media_type` — this one patches the
  **code default**, not existing rows), `defines.inc.php` again
  (`ZBX_DEFAULT_AGENT`), `/etc/php/8.3/apache2/php.ini` (`max_input_time` 60→300),
  `administration.gui.edit.php`, `httptest.inc.php`.
- **Step `[12/12]`**: the `zabbix.php` → `vizoure.php` URL rebrand. Copies
  `zabbix.php` to a new `vizoure.php` (both files now coexist and both work),
  patches `include/classes/core/ZBase.php` to accept `vizoure.php` as a valid
  routing entry point and to redirect to `vizoure.php?action=system.warning`
  instead of the zabbix.php equivalent, then blanket `grep -rl` + `sed` across
  `js/`, `widgets/`, `include/`, and `app/` replacing quoted `'zabbix.php'` /
  `"zabbix.php"` / `zabbix.php?` references — this is the **one** place the
  script does a tree-wide sweep rather than a named-file patch, and it explicitly
  excludes `.bak`/`.po`/`.mo` files.
- **Step `[13]` (unlabeled "ADDITIONAL SCATTERED LABELS")**: `ITEM_TYPE_ZABBIX_ACTIVE`
  "(active)" variant, `connector.edit.php` (Zabbix Streaming Protocol string),
  `administration.miscconfig.edit.php` + `proxy.edit.php` (5 vault/secret-retrieval
  strings each), `CItemData.php` (2 strings), every `widgets/*/manifest.json`
  (`"author": "Zabbix"` → `"Vizoure"`), `include/page_header.php` (drops the
  `Zabbix` fallback in the page-title-or-empty ternary), `CHtmlPageHeader.php`
  (HTML `<meta content="Zabbix SIA">` → `"Vizoure"`).
- Final actual `systemctl restart apache2` call.

**Design pattern to follow when adding a new string:** every patch above targets one
specific file and one specific string/line via `sed -i "s/<exact old>/<exact new>/"`
guarded by `[ -f "$FILE" ]`, never a recursive find-and-replace over the whole UI tree
(except the `zabbix.php`→`vizoure.php` step, which has its own narrow exclusions). A
blanket `Zabbix`→`Vizoure` sweep is deliberately avoided because it would also rewrite
package-identifying strings, config file paths, and upstream documentation URLs that
must stay pointed at the real Zabbix.

## Layer 3 — Runtime API calls

`scripts/install-nms.sh` step `[9/9]`, after Apache + the API respond (polled for up
to 120s):
1. `user.login` as `Admin`/`zabbix` (the factory-default Zabbix credentials) to get a bearer token.
2. `settings.update` → `server_name: "Vizoure NMS"`.
3. `hostgroup.update` on groupids `1`, `4`, `5`, `2`, `6` → renamed to "Vizoure Servers", "Vizoure NMS Servers", "Discovered Devices", "Linux Servers", "Virtual Machines" respectively (hardcoded numeric IDs — assumes a stock just-imported schema where these IDs are stable).
4. `user.create` → new `admin`/`<WEB_ADMIN_PASSWORD>` account, role id `3`, group id `7`.
5. `host.update` on hostid `10084` (Zabbix's well-known default "Zabbix server" host) → renamed to "Vizoure NMS Server".
6. `dashboard.delete` on ids `["2","57"]` and `map.delete` on id `["1"]` — removes the stock default dashboards/map rather than renaming them.
7. An inline Python block (`dashboard.get`/`dashboard.update` on dashboard id `1`) finds a `gauge` widget literally named "Zabbix server" and renames it to "Memory Utilization", and rewrites any `svggraph` widget field referencing host "Zabbix server" to "Vizoure NMS Server" — this is widget **config data**, not a string label, so it needs the API rather than a file patch.
8. Re-logs-in as the new `admin`/`<WEB_ADMIN_PASSWORD>` account and randomizes the original `Admin` user's password via `openssl rand -base64 24` with `user.update` — the original factory account is disabled, not deleted.

`scripts/upgrade.sh` does **not** repeat any of Layer 3 — it assumes these renames
already happened during the original install and only re-does Layers 1 and 2.

## Layer 4 — Agent packaging (separate mechanism per OS)

Not part of the server rebrand above; each OS agent installer rebrands only the
**packaging wrapper**, never the binary:

- **Windows** (`agent-packaging/windows/vizoure-agent-install.ps1`): downloads the
  stock `zabbix_agent-7.4.9-windows-amd64-openssl.msi` from `cdn.zabbix.com`, installs
  it silently, then deletes the MSI-created `Zabbix Agent` service and recreates an
  equivalent `Vizoure Agent` service pointing at the same `zabbix_agentd.exe` with a
  Vizoure-authored config file.
- **macOS** (`agent-packaging/macos/package.sh`): wraps a pre-existing
  `/usr/local/sbin/vizoure_agentd` binary (not built by anything in this repo) in a
  `pkgbuild` package with a `com.vizoure.agent` LaunchDaemon plist.
- **Linux**: no working mechanism — `agent-packaging/linux/build-agent.sh` is empty.

## Summary: what to touch for a new rename

| You want to rename... | Touch this |
|---|---|
| A string shown in a specific PHP view/controller | `branding/apply-branding.sh` — add a new targeted `sed` for that file, following the existing one-file-one-string pattern. One edit covers both install and upgrade, since `upgrade.sh` calls this same script. |
| An existing value already stored in the DB (host/item/trigger/action/image names) | Both `scripts/install-nms.sh` and `scripts/upgrade.sh` — their DB `UPDATE` statements currently disagree (see "Known issues" below), so a fix applied to only one will not reach the other path. |
| A dashboard/map/widget's stored JSON config | The Layer 3 JSON-RPC block in `scripts/install-nms.sh` only — there is no equivalent step in `scripts/upgrade.sh`. |
| The default value a newly created row gets (vs. an existing row) | The relevant file under `/usr/share/zabbix/ui` via `apply-branding.sh` (e.g. `CMediatypeHelper.php`'s hardcoded default) — separate from the Layer 1 `UPDATE`, which only fixes rows that already exist. |

### Present in `upgrade.sh` only
None — every statement in `upgrade.sh`'s Layer 1 block has an identical counterpart in
`install-nms.sh`. `upgrade.sh` is a strict subset.

### Layer 3 gap (not a Layer 1 issue, recorded here per instruction)
As already noted in the Layer 3 section above: the JSON-RPC calls in
`scripts/install-nms.sh` step `[9/9]` (lines ~170–298) — host group renames, default
host rename, dashboard/map deletion, the dashboard-widget-JSON Python patch, and
disabling the original `Admin` account — have **no equivalent step anywhere in
`scripts/upgrade.sh`**. `upgrade.sh` assumes all of this was already done by the
original install and never repeats or re-checks it.

⚠️ needs confirmation: whether the `upgrade.sh` gaps above are intentional (the
assumption being that these rows, once renamed by `install-nms.sh`, never revert on a
point-release upgrade) or an oversight. The one case that seems most likely to actually
bite is the missing template-description heredoc, since Zabbix point releases do ship
updated/new template descriptions.
